## 1. Public experience, design and routes — [~]
Build a responsive, accessible, fast mobile-first interface for low-cost Android phones and ordinary mobile internet. Use an original dark navy/black base with elegant gold accents, readable text and restrained animation. Use a consistent system for typography, spacing, colors, cards, modals, forms, navigation, notifications and game screens; include clear buttons, loading, validation, empty, success and failure states. Provide configurable brand name/logo placeholder; do not copy another platform's branding or assets. Public routes: home; games catalogue; game details/rules; how it works; FAQ; contact/support; Terms; Privacy; wallet/payment policy; fair-play/dispute policy; responsible gaming/player protection; login; registration; password reset; email verification; account security/session management; custom 404/error pages. Terms and Privacy are accessible before registration and participation; route manifest stays synchronized.

## 2. Authentication and account security — [~]
Implement unique email and username, modern password hashing, email verification, expiring single-use password-reset tokens, secure sessions, logout and session revocation. Apply login rate limiting and brute-force protection, validation on frontend and backend, authorization/security controls, optional 2FA architecture, account status controls, suspicious-account and duplicate-account abuse detection. Free permitted features do not require deposits. Real-money play/withdrawal requires legally required age and identity verification; email verification alone is insufficient. Configure email provider; do not claim delivery, bypass verification or expose secrets/payment/identity data in emails.

## 3. User dashboard and private data — [~]
Show profile; verification state; wallet/available/reserved balances; total deposits/withdrawals; match history; wins/losses/draws/win rate; recent transactions; notifications; active matches; pending withdrawals; security settings; support/dispute requests. Scope every private record to its authenticated owner and prevent URL/API identifier changes from exposing another user's wallet, payment details, identity documents or transaction history.

## 4. Chess and checkers — [~]
Chess is fully playable for two players using a reputable rules engine, with legal server-validated moves, check/checkmate, stalemate, draw conditions, resignation, configurable clocks, turn indicators, reconnection, persistent state and verified final result. Checkers is playable for two players with documented exact ruleset, legal moves, mandatory captures where applicable, multi-jumps, win/loss/draw, resignation, server authority and reconnection. Keep a modular game system for future 8-ball pool, trivia and other skill games, but do not present a future game as playable until implemented and tested. Use original or properly licensed assets/engines.

## 5. Matchmaking, live play and settlement lifecycle — [~]
Player selects game and free match or stake. Backend checks eligibility, account status, balance and limits, creates request, finds compatible opponent, displays stake/fee/payout/rules/cancellation terms, obtains both confirmations, reserves funds atomically and begins only when both are ready. Use WebSockets for game events; implement waiting queues, timeout, ready confirmation, reconnection, graceful cancellation, abandoned-match rules, draw and dispute handling, anti-collusion/suspicious-match detection, rate limits and abuse protection. Server validates moves/results and persists state; finalization and settlement are exactly once. Never trust frontend-submitted results. Release reservations if opponent is not found or match cannot begin, under documented rules.

## 6. PostgreSQL and double-entry ledger — [~]
Use external PostgreSQL with migrations, foreign keys and indexes; integer Kenyan shillings/virtual units or integer minor units only, never floating-point money. Read the user's external connection from protected `DATABASE_URL`, not source. Keep virtual credits (`VKE`) and real cash (`KES`) in distinct wallets, ledger accounts, transaction currencies and row locks: no virtual credit can be withdrawn as cash and no transaction can balance by mixing currencies. Implement wallet accounts, available/reserved balances, deposits, withdrawals, match stakes, prize settlements, platform fees, refunds/reversals, transaction references, idempotency keys, reconciliation records and administrative audit logs. Each ledger transaction has unique identifier, type, source, timestamp, status, idempotency key where applicable and balanced debit/credit entries; database commit rejects missing/unbalanced entries or a currency mismatch. Use DB transactions and row locks/equivalent for reserving, settling and withdrawing. Prevent negative available balance, double-spend, duplicate prizes/deposit credits, unauthorized balance changes, edits/deletion of posted entries and client-side balance manipulation. Correct mistakes with auditable reversing entries. Two KSh 100 stakes in the **virtual-credit** ledger: atomically/idempotently return winner's own KSh 100, credit opponent's KSh 100 less KSh 20 fee, record KSh 20 virtual-fee revenue, release unneeded reservations; winner total is KSh 180 virtual credits. Duplicate settlement/event never pays twice.

## 7. Virtual-credit flows and transparent fee configuration — [~]
Initially use virtual credits and simulated payment integrations. A server-side live-money flag defaults off and guards real deposits, paid matchmaking, cash prizes and live withdrawals; never expose virtual-credit balances to any cash withdrawal API. Live deposit/cash-out paths remain unavailable until a separate cash-backed match and verified payout workflow is implemented and authorized. Simulations are clearly labeled and never described as real provider success. Default platform service fee is configurable at 10% of total virtual-credit pool and snapshotted per match so later config changes cannot alter existing matches. Before commitment show stake, total pool, fee and possible payout. Do not secretly change fee, deduct undisclosed charges or pay the wrong player. KSh 100 + KSh 100 = KSh 200 virtual pool, KSh 20 fee, KSh 180 virtual payout. Simulated successful deposit credits exactly once; failed simulation never credits; duplicate callbacks never duplicate credit. Concurrent withdrawals cannot overspend. Unverified/unauthorized provider payout cannot mark a withdrawal complete. Draw/cancel follows documented settlement/refund policy.

## 8. Courtney Tech M-Pesa gateway and Daraja context — [~]
Use the user's specified `https://pay.courtneytech.space` gateway from the server, not browser JavaScript. The documented Local Phone API uses `B2CCOURTNEY_API_KEY` and `B2CCOURTNEY_API_SECRET` only under `/api/v2/b2c/*`; those keys are distinct from the shared legacy `/v2/stkpush` API credentials. STK uses `POST /api/v2/b2c/stk`, an `Idempotency-Key`, phone, whole-KES amount and reference/description; amounts are documented as KES 1–70,000. Reuse the same idempotency key only for the same request. A successful submission/accepted request is not payment completion. Poll `GET /api/v2/b2c/status?request_id=...` with same credentials until terminal; pending/unknown must not be treated as success or resent with a fresh key.

Safaricom callback goes to Courtney Tech, not this app. Courtney Tech's merchant webhook test delivery is manual-only and marked `test:true`; it is not a live payment event. Do not credit from that test. Keep provider confirmation/audit evidence and reconcile via status polling. Safaricom's official docs describe asynchronous callback processing and B2C production prerequisites; do not invent signature support on the merchant route.

Winner payout uses `POST /api/v2/payouts` only when the key explicitly has `payouts:create`; use an idempotency key and store provider reference/status. Respect provider KYC, payout limits, available balance, readiness and pending safeguards. Unknown/pending stays pending; confirmed success completes; confirmed failure reverses with balanced posting. Do not bypass KYC or blindly retry. Keep separately disclosed provider costs distinct from the 10% game fee. Never register/sign in to the gateway, send a real STK prompt, or initiate payout as part of ordinary build/tests. Obtain credentials through protected secret input only when needed. Keep real-money integration disabled until approvals/permissions/controls are confirmed. Direct Daraja API calls are not made unless separately requested; the Safaricom docs inform product/provider constraints.
