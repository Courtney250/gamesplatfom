# Production-readiness register

This register distinguishes the current free-play implementation from a financial-product launch. It is not a certification, legal opinion or substitute for provider onboarding.

## Implemented controls in this build

- Email/password authentication uses Node `scrypt` hashes, one-time expiring verification/reset tokens stored as hashes, opaque random server sessions stored as hashes, session revocation, CSRF tokens, role checks, generic auth responses and rate limiting.
- HTTPS Preview sessions use `HttpOnly; SameSite=None; Secure` cookies by default. Plain-HTTP local development must be explicitly configured separately.
- API validation, parameterized PostgreSQL queries, per-user scoping, server-authoritative game state, participant-only Socket.IO rooms, move authorization and origin checks.
- Double-entry journals with integer money, a database commit-time balance guard, idempotency and distinct VKE and KES partitions; match settlement uses only the virtual ledger.
- A dedicated test harness blocks remote and non-`duelke_test` PostgreSQL integration targets. Local integration tests exercise account flows, wallet IDOR, match settlement, Checkers state, live sockets, the hard payment gate and disputed-fee reporting.
- Live-money paths default off. The only callable balance adjustment is a visibly labeled, capped, idempotent VKE simulation. Gated KES deposit/withdrawal routes exist, but the app still has no enabled live payment flow or cash-backed paid-match settlement.
- User-scoped KES deposit initiation/status routes use Courtney Tech's documented Local Phone API contract, stable idempotency keys, database-serialized request creation, five-second database-locked status polling, amount matching, and sanitized reconciliation evidence. Finance users can inspect that evidence. PostgreSQL tests prove environment flags cannot bypass the compile-time live-money gate and no provider call is made. Generic user withdrawals are intentionally unsupported: Courtney Tech documents its payout endpoint as a winner-payout product, so the app must not reuse it for cash withdrawals without the provider's explicit confirmation and an authorized product contract.
- Protected admin roles, event audit records, data-minimizing verification workflow, player self-exclusion and support-ticket actions. Disputed completed-match fees are excluded from gross virtual-fee reporting and shown separately; monetary displays use a BigInt-safe formatter.
- A branded client error boundary and public 404 page; unknown production SPA paths return HTTP 404. Unauthenticated admin paths remain login-protected.

## Still required before any real-money launch

1. **Database scope:** do not use the currently submitted all-environments `DATABASE_URL` for preview/testing or writes until its owner confirms it is a dedicated, non-production database and the protected setting is split to the appropriate environment scope. Establish managed backups, restore testing, migration rollback/forward procedures, monitoring and data-retention controls for the chosen provider.
2. **Email:** configure and verify an approved SMTP provider, SPF/DKIM/DMARC, abuse limits, delivery monitoring, and links/origins for each environment. Until then, no real user can complete email verification/reset through the app.
3. **Payment provider:** onboard and verify the intended merchant account, API ownership, Safaricom/provider credentials, API product, callbacks/polling, approved collection destinations, cash balance, KYC, limits and payout scope. Confirm production URL/API contracts, pricing/fees, reconciliation statements and incident escalation with the provider. Do not infer this readiness from API documentation or an accepted STK response.
4. **Cash flows:** real deposit initiation is implemented but untested against a merchant account; provider-confirmed posting, amount mismatch, failure/no-credit, duplicate/concurrent provider polls, and ambiguous timeout cases still need isolated provider-mock and approved merchant-sandbox tests. Generic user withdrawals are not implemented because the documented provider payout is winner-only; obtain written confirmation of an authorized withdrawal product and its callback/status contract before implementing it. Add monitored background reconciliation and operator review for pending/unknown requests, provider statements, refunds/reversals, and audit evidence. Implement and review cash match reservations and exactly-once cash-match settlement before any paid matchmaking. Do not route virtual credits or virtual fees to cash endpoints. No provider call has been made from this build.
5. **Legal/regulatory:** obtain qualified Kenyan legal advice on gambling/skill-game classification, gaming/payment licensing, age limits, consumer protection, tax, privacy/data-protection law, record retention and complaint/withdrawal obligations. Establish and evidence any required approvals before paid entry or prizes. The policy text is a product draft, not legal advice or a representation of compliance.
6. **Identity and safety:** determine lawful, proportionate age/identity and sanctions requirements with counsel/provider. Implement authorized verification and appeals, safeguarding of sensitive evidence, account-compromise handling, fraud/collusion review, human review and data minimization. The current minimal verification status screen is not identity verification.
7. **Security/operations:** independent application and infrastructure security review; threat model/penetration test; secrets rotation, TLS, session recovery, backup/restore, least-privilege provider accounts, audit retention, alerting, incident response, rate-limit/WAF and abuse review; verify the production database isolation boundary and concurrent rollout compatibility.
8. **Evidence:** current checks pass strict typecheck, 9 unit tests, both local PostgreSQL/Socket.IO integration suites, production build, and all 7 Playwright tests in both Chromium and WebKit. Landing-page responsive overflow is checked at 320, 360, 375, 414, 768, 1024 and 1440px; tests also cover navigation/CTAs, keyboard focus, reduced-motion behavior, mobile menu, local artwork loading, fee/cash disclosures, registration validation, custom 404 and unauthenticated admin protection. This is browser-engine emulation, not a physical Android/iOS device test. Still run browser-level E2E across account, wallet, full Chess/Checkers matches, authenticated admin, reconciliation and dispute flows; add isolated provider-mock tests for confirmed deposit, mismatch, error and timeout behavior; include load/concurrency, network interruption, replay/idempotency, and disaster recovery against isolated staging services. Store test reports and resolve all critical/high findings. No provider sandbox or production request was sent.

## Deployment gate

The free-play app may be reviewed in the managed Preview after the owner resolves the outstanding development database scope question. No source commit, GitHub push or production publication is authorized or performed. `REAL_MONEY_ENABLED` and `COURTNEY_PAYOUTS_ENABLED` must remain false. A successful frontend/server build or sandbox test does not satisfy the launch gates above.
